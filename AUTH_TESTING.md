# Проверка авторизации, бронирования и email

Запускай этот чеклист после любых изменений в авторизации, бронировании или отправке писем.
Проверяй Firebase Console → Authentication → Users и Firestore → users/ одновременно.

---

## 1. Новый пользователь email/password

1. Открой сайт в режиме инкогнито (без существующей сессии).
2. Открой модальное окно бронирования или кнопку «Войти» → вкладка «Регистрация».
3. Заполни имя, новый email, пароль → отправь.
4. **Ожидаемый результат**: окно закрывается, пользователь вошёл.
5. Firebase Console → Authentication → Users → email появился.
6. Firestore → users/{uid} → документ существует с полями:
   - `role: "user"`, `provider: "email"`, `displayName`, `email`, `createdAt`, `lastLoginAt`
7. Создай бронь.
8. **Ожидаемый результат**: бронь появилась в Firestore → bookings/{id} с `userId` = uid пользователя.
9. **Ожидаемый результат**: на почту пришло письмо-подтверждение.

---

## 2. Повторная регистрация уже существующего email

1. На вкладке «Регистрация» введи email уже зарегистрированного аккаунта.
2. **Ожидаемый результат**: сообщение об ошибке «Этот email уже зарегистрирован. Попробуйте войти.»
3. **Ожидаемый результат**: форма автоматически переключается на вкладку «Вход».
4. **Ожидаемый результат**: поле email сохраняет введённый адрес.
5. Введи правильный пароль → вход выполнен.
6. Firestore → users/{uid} → `lastLoginAt` обновился; `role` не изменился.

---

## 3. Вход через Google

1. Нажми «Войти через Google» в любом месте сайта.
2. Выбери аккаунт Google во всплывающем окне.
3. **Ожидаемый результат**: окно закрылось, пользователь вошёл.
4. Firebase Console → Authentication → Users → Google-аккаунт появился.
5. Firestore → users/{uid} → документ с `provider: "google"`, поле `photoURL` заполнено.
6. Создай бронь.
7. **Ожидаемый результат**: письмо пришло на email Google-аккаунта.

**Граничные случаи:**
- Закрыть окно Google без выбора аккаунта → ошибка не отображается (тихий выход).
- Браузер заблокировал окно → сообщение «Всплывающее окно заблокировано браузером».
- Домен не добавлен в Firebase → сообщение о неавторизованном домене.

---

## 4. Проверка аккаунта администратора

1. Войди с email/паролем администратора.
2. Firestore → users/{uid} → должно быть `role: "admin"`.
3. Выйди и войди снова.
4. **Ожидаемый результат**: `role` остаётся `"admin"` — функция `ensureUserDocument` никогда не перезаписывает роль.
5. Перейди по адресу `/admin` → страница AdminPage загружается без редиректа.
6. Убедись, что вкладка «Зрители» в AdminPage показывает всех пользователей из Firestore.

---

## 5. Проверка бронирования — bank_transfer

1. Войди как обычный пользователь.
2. Открой модальное окно бронирования → выбери «Банковский перевод».
3. Создай бронь.
4. **Ожидаемый результат**: экран успеха показывает:
   - Код брони (формат XXXX-XXXX)
   - Реквизиты для перевода (получатель, IBAN, BIC, назначение платежа)
   - Кнопку «Скопировать реквизиты»
5. Firestore → bookings/{id}:
   - `paymentMethod: "bank_transfer"`
   - `paymentStatus: "awaiting_transfer"`
   - `status: "pending"`
   - `paymentExpiresAt` — ровно +24 часа от создания
   - `showStartAt` — абсолютный момент начала спектакля (Timestamp, не строка)
6. В личном кабинете бронь появилась с напоминанием об оплате.
7. На почту пришло письмо с реквизитами банковского перевода.

---

## 6. Проверка бронирования — on_site

1. Войди как обычный пользователь.
2. Открой модальное окно бронирования → выбери «Оплата на месте».
3. Создай бронь.
4. **Ожидаемый результат**: экран успеха показывает:
   - Код брони
   - Сообщение «Оплата на месте перед спектаклем»
   - Без реквизитов банковского перевода
5. Firestore → bookings/{id}:
   - `paymentMethod: "on_site"`
   - `paymentStatus: "not_paid"`
   - `status: "pending"`
   - `showStartAt` — абсолютный момент начала спектакля (Timestamp, не строка)
6. На почту пришло письмо без банковских реквизитов.

---

## 7. Проверка письма при создании брони

1. Создай бронь любым способом (bank_transfer или on_site).
2. **Ожидаемый результат** — письмо содержит:
   - Тему: «Бронирование принято: [название спектакля]»
   - Имя зрителя
   - Название спектакля, дату, время
   - Количество билетов и сумму
   - Код брони (крупно)
   - Если bank_transfer: реквизиты для перевода (IBAN, BIC, назначение)
   - Если on_site: сообщение об оплате на месте
3. Одно событие = одно письмо. Повторных писем быть не должно.

---

## 8. Проверка письма при подтверждении брони

1. Войди как администратор → перейди на `/admin`.
2. Найди бронь со статусом «Ожидает».
3. Нажми кнопку «Подтвердить».
4. **Ожидаемый результат**: статус в таблице сменился на «Подтверждено».
5. **Ожидаемый результат**: зрителю пришло письмо:
   - Тема: «Бронирование подтверждено: [спектакль]»
   - «Ваше место зарезервировано. Приходите за 15 минут до начала.»
   - Код брони
6. Если нажать «Подтвердить» повторно на уже подтверждённой брони → письмо не отправляется (защита от дублей).

---

## 9. Проверка письма при отметке «Оплачено»

1. Войди как администратор → перейди на `/admin`.
2. Найди бронь со статусом оплаты «Не оплачено» или «Ожидает перевода».
3. Нажми кнопку «Оплачено».
4. **Ожидаемый результат**: статус оплаты сменился на «Оплачено».
5. **Ожидаемый результат**: зрителю пришло письмо:
   - Тема: «Оплата получена: [спектакль]»
   - Код брони
   - Если бронь уже подтверждена: «Ваша бронь подтверждена. Ждём вас в театре!»
   - Если бронь ещё ожидает: «Бронь ожидает подтверждения.»
6. Если нажать «Оплачено» повторно → письмо не отправляется.
7. При нажатии «Не оплачено» → письмо не отправляется.

---

## 10. Как удалить тестового пользователя полностью

**Шаг 1 — Firebase Authentication:**
- Firebase Console → Authentication → Users
- Найди email → нажми ⋮ → «Delete account»

**Шаг 2 — документ пользователя в Firestore:**
- Firestore → Коллекция `users` → найди документ с нужным uid → удали

**Шаг 3 — тестовые брони:**
- Firestore → Коллекция `bookings`
- Фильтр: `userId` == uid (используй «Filter» в консоли)
- Удали все найденные документы

> После удаления: email можно зарегистрировать заново без конфликтов.

## 11. Что проверять в Firebase Console

| Настройка | Где находится | Нужное значение |
|-----------|---------------|-----------------|
| Вход через email/пароль | Authentication → Sign-in method | Включён |
| Вход через Google | Authentication → Sign-in method | Включён |
| Авторизованные домены | Authentication → Settings → Authorized domains | `localhost` + домен Vercel |
| Правила Firestore | Firestore → Rules | Развёрнуты из `firestore.rules` |

Служебные коллекции пишет только сервер через Admin SDK, клиенту они закрыты
правилами — если видишь в них записи от клиента, что-то не так:
`showCounters`, `loyaltyState`, `idempotencyKeys`, `rateLimits`,
`audienceCounted`, `emailLog`.

Правила деплоятся отдельно от кода:
`npx -y firebase-tools@latest deploy --only firestore:rules`

## 12. Что проверять в Resend

1. Перейди на [resend.com](https://resend.com) → Dashboard → Emails.
2. Найди письмо по теме или адресу получателя.
3. **Проверь**: статус `Delivered`, а не `Bounced` или `Failed`.
4. **Проверь**: письмо отображается корректно (HTML + plain text версия).
5. **Проверь**: отправитель — `EMAIL_FROM` из Vercel Dashboard.
6. **Проверь**: в письме нет реальных ключей (только плейсхолдеры IBAN/BIC до продакшена).

---

## 13. Что проверять в Vercel

1. Vercel Dashboard → проект → Deployments → последний деплой → статус `Ready`.
2. Functions → посмотри логи. Функций теперь семь:
   `create-booking`, `cancel-booking`, `checkin-ticket`, `show-availability`,
   `register-audience`, `expire-bookings`, `send-email`, `delete-user`.
3. Settings → Environment Variables — должны быть заполнены:
   `RESEND_API_KEY`, `EMAIL_FROM`, `FIREBASE_SERVICE_ACCOUNT`, `ALLOWED_ORIGIN`,
   `CRON_SECRET`.
   Без `FIREBASE_SERVICE_ACCOUNT` не работает ни бронирование, ни отмена, ни
   проверка билетов. Без `CRON_SECRET` endpoint протухания примет запрос от кого угодно.
4. Settings → Cron Jobs → задание `/api/expire-bookings` должно быть активно
   (расписание задано в `vercel.json`).
5. **Проверь**: в Environment Variables нет реальных банковских реквизитов или секретных ключей без необходимости.
6. **Проверь**: `.env` файл не попал в деплой (он должен быть в `.gitignore`).
7. **Проверь**: ни одна серверная переменная не имеет префикса `VITE_` — иначе она попадёт в браузерный бандл.

## 14. Проверка рассылки нового спектакля

1. Убедись, что хотя бы один пользователь (не admin) зарегистрирован и у него включены уведомления:
   Firestore → users/{uid} → `notifications: true`.
2. Войди как администратор → перейди на `/admin`.
3. Перейди на вкладку «Рассылка».
4. Выбери спектакль из выпадающего списка.
5. Нажми кнопку «Отправить рассылку».
6. **Ожидаемый результат**: появился запрос подтверждения с числом получателей.
7. Подтверди отправку.
8. **Ожидаемый результат**: кнопка недоступна пока идёт отправка (статус «Отправляется…»).
9. **Ожидаемый результат**: после завершения виден результат:
   - сколько писем отправлено успешно;
   - если были ошибки — список email с ошибками.
10. Проверь Resend → Dashboard → Emails: письмо должно появиться со статусом `Delivered`.
11. **Проверь**: рассылка НЕ запускается автоматически при добавлении спектакля.
12. **Проверь**: пользователи с `notifications: false` или без email письмо не получили.
13. **Проверь**: admin из рассылки исключён.

**Что делать, если письмо не пришло:**
- Resend → Emails → проверь статус и ошибку.
- Vercel → Functions → `api/send-email` → посмотри логи.
- Проверь, что `RESEND_API_KEY` и `EMAIL_FROM` заполнены в Vercel Dashboard.
- С `onboarding@resend.dev` письма уходят только на email владельца Resend-аккаунта.
  Для отправки всем нужен собственный домен в Resend.

## 15. Если пользователь не указал ticketCode в переводе

Автоматически определить платёж без ticketCode невозможно без банковского API.

Алгоритм для администратора:
1. Открой банковскую выписку.
2. Сверь сумму перевода с суммой брони.
3. Сверь имя/дату с данными в AdminPage.
4. При необходимости свяжись с пользователем через email из брони.
5. Вручную нажми «Оплачено» в AdminPage — это автоматически подтвердит бронь.

## 16. Проверка разделов «Мои билеты» и «Мои спектакли»

1. Войди как пользователь с несколькими бронированиями в разных статусах.
2. Открой личный кабинет.
3. **Ожидаемый результат**: раздел «Мои билеты» показывает брони со статусом pending / confirmed / cancelled.
4. **Ожидаемый результат**: раздел «Мои спектакли» показывает брони status=attended и вычисленно посещённые (confirmed+paid, спектакль закончился 2+ ч назад).
5. **Ожидаемый результат**: каждая карточка показывает цветной глиф спектакля слева (если showId совпадает с известным спектаклем).
6. **Ожидаемый результат**: счётчик посещений и прогресс-бар находятся в секции «Мои спектакли».
7. Если нет посещённых спектаклей — счётчик всё равно отображается с текстом «Вы ещё не посетили ни одного спектакля».

## 17. Отмена брони зрителем

Отмена идёт через `/api/cancel-booking`; напрямую в Firestore клиент бронь не пишет.

1. Создай бронь с оплатой на месте, войди как её владелец → личный кабинет.
2. Нажми «Отменить бронь», выбери причину, подтверди.
3. **Ожидаемый результат**: бронь стала `status: "cancelled"`, в документе появились
   `cancelledBy: "user"`, `cancelReason`, `cancelledAt`.
4. Попробуй отменить ещё раз — кнопки быть не должно.
5. Теперь отметь другую бронь как оплаченную из админки и вернись в кабинет.
6. **Ожидаемый результат**: у оплаченной брони кнопки отмены НЕТ.
   Это бизнес-правило: оплата окончательна, автоматических возвратов в системе нет.
7. Проверь, что сервер отказывает и в обход интерфейса: отправь запрос на
   `/api/cancel-booking` с `bookingId` оплаченной брони — должен вернуться 409
   с причиной `already_paid`.
8. Проверь чужую бронь: с токеном другого пользователя тот же запрос должен
   вернуть 404 (чужая бронь не должна «светиться» отдельным кодом ответа).

## 18. Вместимость зала

Проверка вместимости живёт ТОЛЬКО на сервере, в транзакции.

1. Открой модальное окно бронирования.
2. **Ожидаемый результат**: показан реальный остаток мест. Если `/api/*` недоступен
   (например, локальный `npm run dev`), индикатор просто скрыт — выдуманного числа
   «свободен весь зал» быть не должно.
3. Набери броней до предела `THEATRE_CAPACITY` (значение в `api/_lib/shows.ts`).
4. **Ожидаемый результат**: следующая бронь отклоняется, интерфейс пишет,
   что мест не осталось.
5. Отмени одну бронь и обнови страницу.
6. **Ожидаемый результат**: место освободилось, остаток вырос.
7. Попробуй заказать больше билетов, чем осталось — сервер должен ответить
   `capacity_exceeded` и вернуть фактический остаток.

## 19. Протухание неоплаченного перевода

1. Создай бронь с банковским переводом.
2. В Firestore вручную сдвинь `paymentExpiresAt` в прошлое.
3. Дождись запуска задания по расписанию (или вызови `/api/expire-bookings`
   с заголовком `Authorization: Bearer <CRON_SECRET>`).
4. **Ожидаемый результат**: `paymentStatus: "expired"`, `status: "cancelled"`,
   появилось поле `expiredAt`.
5. **Ожидаемый результат**: место освободилось — остаток в модалке бронирования вырос.
6. Важно: протухание больше НЕ зависит от того, откроет ли кто-нибудь личный
   кабинет или админку.

## 20. Проверка билета и проход

1. Войди администратором → «Проверка билетов».
2. Отсканируй QR оплаченного билета на сегодняшний спектакль.
3. **Ожидаемый результат**: «БИЛЕТ ДЕЙСТВИТЕЛЕН», кнопка «Отметить посещение».
4. Отметь проход. В Firestore появились `attendedAt` и `attendedBy` (uid сотрудника).
5. Отсканируй тот же код повторно.
6. **Ожидаемый результат**: «БИЛЕТ УЖЕ ИСПОЛЬЗОВАН».
7. Отсканируй код билета на ПРОШЕДШИЙ спектакль.
8. **Ожидаемый результат**: билет недействителен, причина — «Билет на прошедший
   спектакль». Существование кода в базе больше не делает билет действительным.
9. Отсканируй неоплаченный билет с оплатой на месте → нажми «Оплачено».
10. **Ожидаемый результат**: бронь стала `paid` + `confirmed`, и зрителю ушло
    письмо об оплате — то же самое, что отправляет админка.
11. По возможности проверь одновременный скан одного кода с двух устройств:
    успешным должен оказаться ровно один.
12. Открой ссылку из QR без активной admin-сессии.
13. **Ожидаемый результат**: код билета НЕ потерян — он показан на экране,
    рядом форма входа, после входа проверка продолжается сама.

## 21. Повторная отправка формы бронирования

1. Открой форму бронирования и быстро нажми Enter дважды подряд.
2. **Ожидаемый результат**: создалась ОДНА бронь.
3. Проверь в Firestore коллекцию `idempotencyKeys` — на бронь должен появиться
   один документ вида `booking_<uid>_<key>`.
4. Закрой и снова открой модалку, забронируй ещё раз осознанно.
5. **Ожидаемый результат**: вторая бронь создалась штатно — ключ обновляется
   при открытии модалки, поэтому новая покупка не блокируется.

## 22. Согласие на cookie и аналитика

1. Открой сайт в режиме инкогнито.
2. **Ожидаемый результат**: показан баннер согласия; в Network НЕТ запросов
   к `googletagmanager.com`; в консоли `typeof window.gtag === 'undefined'`.
3. Нажми «Отказаться», перезагрузи страницу.
4. **Ожидаемый результат**: баннер больше не появляется, GA по-прежнему не грузится.
5. Очисти хранилище, нажми «Принять».
6. **Ожидаемый результат**: скрипт GA загрузился, `window.gtag` — функция.
7. Vercel Analytics и Speed Insights работают в любом случае — они без cookie.

## 23. Мелочи, которые легко упустить

1. Открой `/#/любой-несуществующий-адрес` → должна быть страница 404 с кнопкой
   на главную, а не пустой экран.
2. Переключи тему на светлую и перезагрузи → тема должна сохраниться.
3. Войди пользователем, у которого в профиле `language: "fr"`, на «новом»
   устройстве → интерфейс должен переключиться на французский.
4. Во французской версии проверь заголовки: «À propos», «Équipe», «Répertoire»,
   «Côte d'Azur» — все буквы должны быть набраны ОДНИМ шрифтом, без разнобоя.
5. Открой любую модалку и нажми Escape → должна закрыться, фокус вернуться
   на кнопку, которая её открыла. Tab внутри модалки не должен уходить на фон.
6. Скачай PDF-билет в русской и французской версии.
7. Проверь сайт на ширине 320px — заголовок «TÊTE À TÊTE» не должен обрезаться.

## Дополнительные заметки

- `ensureUserDocument` находится в `src/context/AuthContext.tsx`.
- Вызывается из `onAuthStateChanged`, `signInWithGoogle`, `signInWithEmail`.
- `signUpWithEmail` пишет документ явно, чтобы сохранить `displayName` из формы.
- Публичный счётчик зрителей увеличивает СЕРВЕР (`/api/register-audience`),
  ровно один раз на пользователя — отметка `audienceCounted/{uid}`.
  Клиент в `stats` не пишет вообще, правила это запрещают.
- Email получателя в брони: `user.email ?? userProfile?.email ?? ''` (сначала Firebase Auth).
- Одна бронь = одно письмо при создании. Письма при смене статуса — только когда статус действительно меняется.
- Отправка писем ограничена: 12 писем в час обычному пользователю, 600 — администратору.
  При превышении endpoint отвечает 429; в рассылке это заметно как «не отправлено».
- Письмо-подтверждение брони требует `ticketCode` и проверяется на принадлежность
  брони вызывающему — просто так отправить письмо от имени театра нельзя.
- Техническое состояние доставки пишется в `emailLog` (тип, uid, статус, код ответа
  провайдера). Адрес получателя туда намеренно не дублируется.
- Реальные реквизиты театра (IBAN/BIC) нужно вписать в `src/config/payment.ts` перед продакшеном.
- Не вставлять банковские реквизиты в `.env` или `.env.example`.

## 1. Current Architecture

```
Браузер (Vite + React 19, HashRouter)
 ├─ Лендинг / BookingModal / ProfileDrawer (кабинет) / AdminPage / TicketCheckPage
 ├─ Firebase Auth + Firestore client SDK (ленивая загрузка из AuthContext)
 │    • зритель: читает свои bookings (onSnapshot), пишет свой users/{uid}
 │    • admin: читает всё, ПИШЕТ bookings напрямую (статус/оплата из админки)
 └─ fetch → /api/* (Vercel Functions, Bearer ID-token)

api/ (10 тонких handler'ов)  →  server/ (сервисы, Admin SDK, транзакции)  →  Firestore
shared/  — изоморфно: каталог спектаклей, правила брони, время сеанса, контракты API
```

Коллекции: `bookings`, `users`, `showCounters` (точка конфликта транзакций), `loyaltyState`,
`idempotencyKeys`, `rateLimits`, `audienceCounted`, `emailLog`, `stats`, `newsletterLocks`.
Индексы: только автоматические однопольные (`firestore.indexes.json` пуст) — все запросы
однопольные (`showId ==`, `userId ==`, `ticketCode ==`, `paymentStatus ==`), составных нет.

Сильные стороны, которые стоит сохранить: цены/статусы/код считает только сервер; вместимость
и лояльность — в одной транзакции с «точками конфликта»; идемпотентность создания; check-in —
атомарная транзакция; cron fail-closed; CORS по белому списку; тонкие handler'ы + чистые правила
в `shared/domain` с тестами; архитектурные тесты границ.

## 2. Booking Lifecycle (как реально работает)

| Шаг | Где | Поля `bookings/{id}` |
|---|---|---|
| Выбор спектакля и тарифа | `BookingModal` (только авторизованные; шаг `auth` встроен) | — |
| Создание | `POST /api/create-booking` → `booking.service.ts`, транзакция | `showId, showTitle, showDate, showTime, showStartAt, userId, userName, userEmail, userPhone, ticketsCount, seatsCount, ticketType, priceInfo, totalAmount, ticketCode, status='pending', paymentMethod, paymentStatus ('awaiting_transfer' \| 'not_paid'), comment, lang, createdAt`, для перевода `paymentReference, paymentExpiresAt (+24ч), paymentAccountId`, для скидки `originalAmount, loyaltyDiscount*` |
| Письмо «бронь принята» | **браузер** после ответа API → `/api/send-email` | `emailLog` |
| Оплата переводом | вручную в банке; админ жмёт «Оплачено» | `paymentStatus='paid', status='confirmed', paidAt, paidBy` ✅ |
| Оплата на месте | сканер: «Принять X € и пропустить» / «Только принять оплату» | то же + `attendedAt/By` |
| Протухание перевода | cron 03:00 UTC + фоллбек при открытии кабинета/админки | `paymentStatus='expired', status='cancelled', expiredAt` |
| Отмена зрителем | `POST /api/cancel-booking` (не paid, не attended, до начала) | `status='cancelled', cancelledBy='user', cancelReason, cancelComment, cancelledAt` |
| Отмена админом | админка, Firestore напрямую | `status='cancelled'`, теперь + `cancelledBy='admin', cancelledAt` ✅ |
| Проход | `POST /api/checkin-ticket` `mark_attended` / `group_checkin` | `status='attended', attendedAt, attendedBy` |
| Удаление | `POST /api/delete-booking` (только cancelled) | hard delete + ключ идемпотентности |

Сценарии: «гость без аккаунта» **не существует** — бронь требует входа. Мест (seat map) нет —
продаются «места в зале» (capacity 50), `seatsCount` = число людей (семейный тариф = 3).
Онлайн-оплаты (Stripe и т. п.) **нет** — только перевод и касса.

## 3. Payment Lifecycle и модель статусов

Сейчас `status` одновременно описывает бронь **и** посещение (`attended`), а `paymentStatus`
содержит **и** оплату, **и** «протухание» (`expired`). Реальные сочетания:

| status \ paymentStatus | not_paid | awaiting_transfer | paid | expired |
|---|---|---|---|---|
| pending | касса, ждём | перевод, ждём | (невозможно штатно) | (нет) |
| confirmed | после «снять оплату» | — | **билет** | — |
| attended | — | — | прошёл | — |
| cancelled | отмена | — | «отменена, деньги у театра» | протух перевод |

Оценка: смешение есть (P2 архитектурный долг), но **ломать схему не нужно**: единые правила уже
вынесены в `shared/domain/bookingRules.ts` (`occupiesCapacity`, `isBookingAttended`,
`canUserCancel`, `describeStateIssue`, теперь и `isScannableTicket` ✅). В v2 предлагается
добавить вычисляемые представления, а не новые поля (см. §12).

Разные названия одного состояния: «оплачено» везде = `paymentStatus === 'paid'` (нет `isPaid`,
`paid: true`) — ок. Но «можно ли пройти» было записано трижды разными выражениями (кабинет,
карточка сканера, групповой сервис) — кабинет и письмо теперь на `isScannableTicket` ✅.

## 4. Ticket / PDF / QR Lifecycle

* **Код брони** `XXXX-XXXX`, 31 символ без 0/O/1/I/L, `crypto.randomInt` — только сервер.
  Уникальность не проверяется (31⁸ ≈ 8.5·10¹¹; вероятность коллизии ничтожна) ℹ️.
* **QR** кодирует URL `https://…/#/admin/checkin?ticket=CODE` — открывается обычной камерой
  телефона. Формат вынесен в `shared/domain/ticketCode.ts` ✅ и общий для кабинета, PDF и письма.
* **PDF** генерируется **в браузере зрителя** (`jspdf`, лениво) из живой брони (onSnapshot) и
  нигде не хранится → устаревшего PDF не бывает по построению. Это правильная архитектура для
  кабинета, её сохраняем. Добавлено ✅: штамп **PAYÉ / ОПЛАЧЕНО / PAID** или
  **PAIEMENT SUR PLACE / ОПЛАТА НА МЕСТЕ**, строка «места» для семейного тарифа. RU-билет:
  подписи транслитом (нет кириллического TTF для текста), штамп — кириллицей декоративным шрифтом.
* **Письма**: HTML собирается в браузере, `/api/send-email` проверяет права и шлёт через Resend.
  До этой сессии **ни одно письмо не содержало QR** — только «откройте личный кабинет».
  Теперь ✅ сервер для `booking-confirmation` и `payment-paid` находит бронь по коду и, если по
  ней можно пройти, вкладывает QR inline (`cid:`); если Resend отвергнет вложение — письмо уходит
  без QR, а не теряется.

## 5. Check-in Lifecycle

`/admin/checkin` (только admin): камера (`html5-qrcode`), файл/PDF, ссылка из QR.
`inspect` — только чтение (можно сканировать сколько угодно); `mark_attended`, `mark_paid`,
`group_checkin` — одна транзакция; второй скан получает `already_attended`.
Групповой проход: все активные брони одного аккаунта на один сеанс по любому QR.

Было плохо для «очереди из 40 человек» — исправлено ✅:
* не было ручного ввода кода и поиска по имени/e-mail/телефону → добавлена панель
  «Нет QR? Найдите бронь» с выбором сеанса (по умолчанию текущий), локальный фильтр;
* неоплаченный билет «на месте» показывался **зелёным «БИЛЕТ ДЕЙСТВИТЕЛЕН»** → теперь
  янтарный «НЕ ОПЛАЧЕНО · ПРИНЯТЬ 40 €» с кнопкой «Принять 40 € и пропустить» (одна транзакция);
* сразу после успешной отметки показывалось «⚠️ БИЛЕТ УЖЕ ИСПОЛЬЗОВАН» → теперь «ПРОХОД ОТМЕЧЕН»;
  повторный скан показывает **время первого прохода** (`attendedAtMs`);
* проход по оплаченному билету требовал диалог подтверждения → одно нажатие; подтверждение
  осталось только там, где принимаются деньги;
* после результата нужно было вернуться на стартовый экран → «Сканировать следующий» сразу
  открывает камеру;
* **билет на другой вечер показывался зелёным и «сжигался»** (зритель перепутал дату →
  на свой вечер «уже использован») → сервер отказывает `too_early` (проход открывается за 4 ч до
  начала), карточка «БИЛЕТ НА ДРУГОЙ ДЕНЬ»; оплату заранее принять по-прежнему можно;
* эмодзи ❌⚠️✅🚫 заменены иконками Tabler (правило дизайн-системы).

## 12. Theatre Ticket System v2 (без переписывания)

**Data model** — расширяем `bookings`, не заменяем:

  `paymentState()` → `'pay_at_venue' | 'awaiting_transfer' | 'paid' | 'expired' | ...`,
  `attendanceState()` — UI и письма читают их, а не сырые поля.

**API** (≤ 12 функций): объединить админские действия в `/api/admin-booking`
(`action: mark_paid | mark_unpaid | cancel | resend_ticket`) — транзакция, аудит,
письмо на сервере; `api/checkin-ticket` не трогаем; `create-booking` сам шлёт подтверждение.

**Email flow**: шаблоны из `src/services/email/templates` → `shared/email/templates`
(они уже чистые функции без DOM). Сервер строит HTML + QR (уже есть `withTicketQr`), клиент
перестаёт присылать HTML — закрывается и «письмо себе с произвольным HTML».

**PDF flow**: оставить генерацию в браузере для кабинета (актуально по построению). Для письма —
либо PDF-вложение, сгенерированное на сервере тем же `buildTicketPdf` (вынести в shared, шрифты
читать с диска), либо ссылка «Скачать билет» на страницу `/#/ticket?code=…&t=<HMAC>` без входа.
Небезопасную публичную ссылку по одному коду не делать: нужен HMAC-токен (`TICKET_LINK_SECRET`),

**QR flow**: единый URL (готово). Подпись QR не нужна — код проверяется сервером и одноразовый.

**Check-in flow / Admin UI**: (готово) скан → карточка → одно нажатие → «Сканировать следующий»;
поиск без QR. Дальше: режим «день спектакля» — список зрителей сеанса с отметками и
счётчиком «пришло X из Y», офлайн-кэш списка.

**User UI**: в кабинете первым блоком «Ближайший билет» с QR развёрнутым по умолчанию; кнопки
«Скачать PDF», «В календарь».

**Firebase changes**: правила не ослаблять. После перевода админских записей на сервер —
сузить `allow update: if isAdmin()` до `false` для полей статуса (или целиком), оставив чтение.

**Migration**: схема не меняется; новые поля опциональны; старые брони без `showStartAt`
уже поддерживаются (`bookingOccurrenceStartUtcMs`).

## Что сделано в этой сессии

1. **Cron протухания** — транзакция на каждую бронь с повторной проверкой; оплата, отмеченная
   в момент запуска, больше не затирается.
2. **Записи админки** — транзакция + проверка «бронь не изменилась»; при конфликте понятная
   ошибка и перечитывание списка; аудит `paidBy` и `cancelledBy/cancelledAt` для админа;
   фоновое протухание из кабинета/админки — тоже транзакцией (поля в пределах правил).
3. **Check-in сервер** — `too_early` для `mark_attended` и `group_checkin`; в ответе `attendedAtMs`.
4. **Экран проверки** — поиск без QR, ручной ввод кода (регистр/пробелы/без дефиса),
   «Принять X € и пропустить», проход одним нажатием, «ПРОХОД ОТМЕЧЕН» vs «УЖЕ ИСПОЛЬЗОВАН · в 19:42»,
   «БИЛЕТ НА ДРУГОЙ ДЕНЬ», «Сканировать следующий», иконки вместо эмодзи.
5. **Админка «Брони»** — поиск, кнопка «Обновить», баннер ошибок любых действий, время оплаты/прохода.
6. **PDF** — штамп оплаты, места семейного тарифа.
7. **Письма** — QR-билет inline в «бронь принята» (касса) и «оплата получена»; фоллбек без QR.
8. **Единые правила** — `ticketCheckUrl`, `normalizeTicketCodeInput`, `isScannableTicket`.
9. Документация: `CLAUDE.md` (неточность «клиент не пишет в bookings»), `.env.example`.
10. Тесты: +47 (поиск, нормализация кода, окно прохода, гонка cron, штамп PDF, QR в письме, экран).
